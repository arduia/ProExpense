# Lint Retrospective — recurring ktlint / detekt / Android-lint findings

> Append-only quick-lookup log, companion to [`SKILL.md`](SKILL.md). Purpose: stop the same
> lint mistake — or the same wasted diagnosis — from happening again in a future session.
>
> **Before diagnosing a new ktlint/detekt/Android-lint failure**, scan the table below for the
> rule ID. If it's already here, apply the documented response instead of re-deriving it.
>
> **After resolving any ktlint/detekt/Android-lint failure this session** — whether the fix was
> code, a baseline regen, or a config change — add a row if the rule/situation isn't already
> covered, or leave it alone if it is (don't duplicate). One row is enough; this is a lookup
> table, not a narrative log (see `.cursor/context/retrospectives.md` for narrative post-mortems
> of larger incidents).

| Rule (tool) | Trigger | Correct response | Do NOT do |
|---|---|---|---|
| `UnusedParameter` (detekt) | A function parameter detekt flags as never referenced in the body. | Treat as a real signal, not baseline noise — read the function body. It has caught genuine bugs here: a `homeCurrencySymbol` param that should have formatted a debt row's amount but the body used a different currency source instead (a param that "looks" used because a same-named sibling function nearby does use it, but this one doesn't). Fix the logic (use the param, or delete it if it's truly redundant with another format source), then re-run detekt to confirm the finding is gone — don't baseline it. | Don't assume it's a pre-existing baseline entry de-keyed by a signature edit (that pattern applies to `LongParameterList`/`LongMethod`/`FunctionNaming`/`CyclomaticComplexMethod`, not `UnusedParameter` — an unused param is either new or was always dead code, never "pre-existing and fine"). |
| `FunctionNaming` (detekt) on `@Composable` functions | Every `@Composable` function is PascalCase by Compose convention, which `FunctionNaming`'s default `functionPattern` (`[a-z][a-zA-Z0-9]*`) always flags. ktlint's `.editorconfig` exempts `@Composable` from its own naming rule; detekt has no built-in exemption. | This is permanent, expected noise — every new/changed `@Composable` needs its own baseline entry. When you add or edit a `@Composable` function (including adding a parameter), regenerate that module's baseline (see `SKILL.md`) rather than trying to silence the rule globally. | Do **not** try `ignoreAnnotated: ['Composable']` (or similar) on the `naming` rule in `config/detekt/detekt.yml` — verified against detekt 1.23.8's bundled `default-detekt-config.yml` (this project's pinned version): `FunctionNaming` has no `ignoreAnnotated` property in this version. `config.validation: true` will hard-fail the build on an unrecognized key. This would need a detekt upgrade to revisit, not a config tweak. |
| `LongParameterList` / `LongMethod` / `CyclomaticComplexMethod` (detekt) on a function whose signature you just edited | Adding/removing/reordering a parameter, or adding a `// comment` inside a multi-line param list, changes the baseline's signature-text key and de-baselines any pre-existing finding for that function. | Read the reported complexity number. If it's roughly what it was before (function was already over threshold, your edit didn't add real branching), regenerate the baseline and diff-verify only the touched signature changed (see `SKILL.md`). If `CyclomaticComplexMethod` newly appears (function was **not** flagged before your change) because you added real branching logic (e.g. a `when` dispatch) directly inside the function body, **extract that logic into a small private helper function instead** — don't baseline genuinely new complexity. Same rule applies to `LongParameterList` if you fixed a param sprawl by bundling related params into a data class (e.g. `HomeLinkNames`, `JournalLinkLabels`): the old finding correctly disappears rather than needing a baseline update. | Don't baseline-regen reflexively on any signature change without first checking whether the *number* moved because of genuinely new logic vs. just parameter-list churn. |
| `MaxLineLength` (detekt, 120 cols) | A `val x = condition1 \|\| condition2 \|\| condition3` (or similar single-expression) line grows past 120 columns after adding a clause. | Extract the condition into a well-named local `val` on its own line(s), or wrap into a multi-line boolean expression per `SKILL.md`'s formatting rules — don't just let the line run long. | — |
| `RememberReturnType` (Android lint, `androidx.compose.runtime`) | `remember(key) { X.apply { property = value } }` or `remember(key) { list.map { ... } }` — the lambda's real return type is `X` / `List<...>` (never `Unit`), but the checker still flags it as returning `Unit` because the lambda's last statement is itself a trailing-lambda call (`.apply { assignment }`, `.map { ... }`) rather than a plain expression. This is a real false positive, not a real Unit-returning bug — verified by reading the actual inferred type. | Extract the body into a small top-level function with an explicit return type (e.g. `private fun calendarAt(epochMillis: Long): Calendar = Calendar.getInstance().apply { timeInMillis = epochMillis }`), then call `remember(key) { calendarAt(epochMillis) }`. A single function-call expression as the lambda body resolves cleanly; this fires as a hard **error** (`abortOnError`), not a baseline-able warning — it does not go in a `lint-baseline.xml`. | Don't assume this is baseline noise like the detekt findings above — Android lint's `lintDebug` task aborts the build on this by default regardless of an existing `lint-baseline.xml` (a *new* finding, not already listed there, still fails). Don't try to "fix" it by adding an explicit type annotation on the `val` alone — the checker inspects the lambda body shape, not the outer `val`'s declared/inferred type. |
| `standard:import-ordering` / `standard:multiline-expression-wrapping` (ktlint) | Hand-editing imports or multi-line lambda/if-else assignments instead of running the formatter. | Run `./gradlew :module:path:ktlintFormat` after any edit that touches imports or reformats a multi-line expression — don't hand-order or hand-wrap and hope it matches ktlint's exact rules. | — |
| `standard:function-signature` (ktlint) | A single-expression function (`fun f(): Boolean = a \|\| b \|\| c`) is over 120 cols. Wrapping just the body onto one indented line after `=` (the `CategoryRowUi(...)` pattern from the formatting-rules section) still fails with "First line of body expression fits on same line as function signature" — `ktlintFormat` doesn't reliably auto-fix this shape either. | For a boolean/operator-chain body (not a call expression), break **each operand onto its own line**, operator at end of line, continuation indented one level past the first: `SHOW_X \|\|\n    this == A \|\|\n    this == B`. This is a different wrap shape than the call-expression case already documented in `SKILL.md`. | Don't keep trying single-line-after-`=` wraps for operator chains — that's the call-expression fix, not this one. |
| `MissingTranslation` (Android lint) | A new `<string>` added to `values/strings.xml` but not to every other `values-*/strings.xml` in that module (this repo ships `values-th/`, `values-my/`). | Add the same string key to every existing locale file in that module in the same change — best-effort translation matching that locale's existing terminology/register is enough; don't leave a locale file behind. | — |
| `standard:function-signature` (ktlint) — trivial single-argument call body (e.g. `error("...")`), not an operator chain | A long signature (long param/return-type names) plus a short call-expression body pushes the combined line past 120 cols. Wrapping the body onto its own indented line after `=` — the normal call-expression fix — gets rejected here with "First line of body expression fits on same line as function signature": ktlint's `function-signature` rule refuses to keep a *trivial* single-argument call on its own line regardless of the resulting combined length, and re-joins it via `ktlintFormat`, which then trips detekt's separate 120-col `MaxLineLength`. | Shorten the line to fit under 120 as one line instead of wrapping: rename an override's local param to something shorter (only if it doesn't change the name ktlint/kotlinc expects — check the interface's declared param name first, an override with a different name still compiles but adds an unrelated "may cause problems with named arguments" warning) or shorten a literal/message string. This case (trivial call body) is different from row above (operator/boolean chain body, which *does* wrap correctly). | Don't keep re-wrapping a trivial call body hoping a different indentation satisfies ktlint — it structurally never will for a single simple call argument. |
| `LongParameterList`/`LongMethod`/`CyclomaticComplexMethod`/`FunctionNaming` (detekt) still fails on `:app:detekt` after regenerating `detekt-baseline-DevDebug.xml`/`-DevRelease.xml`/`-ProductionDebug.xml`/`-ProductionRelease.xml` | `:app` is an Android *application* module (not KMP), so alongside the four flavor-variant `Detekt` tasks (`detektDevDebug`, …) there is also a plain umbrella `detekt` task — its task name is literally `"detekt"`, so `baselineFileFor(name.removePrefix("detekt"))` resolves to the **empty-string branch**: the unsuffixed `app/detekt-baseline.xml`, a fifth, separate baseline file. `verifyAll` depends on it too (its name doesn't end in `"Test"`, so it passes the `isMainVariant` filter alongside the four real variants). Regenerating only the four suffixed baselines leaves this one stale. | After `detektBaselineDevDebug`/`DevRelease`/`ProductionDebug`/`ProductionRelease`, also run `./gradlew :app:detektBaseline` (no suffix) to regenerate `app/detekt-baseline.xml`, then re-verify with `./gradlew :app:detekt` (the umbrella task, not one of the per-variant ones) before assuming the gate is clean. | Don't stop at the four Android-flavor baselines for `:app` specifically — that's sufficient for a pure KMP library module (no umbrella task with real source), but `:app` has this fifth file too. |
| `LongParameterList` (detekt) on a **pre-existing, untouched** `app/src/test/**` helper function, surfaced only by the plain `./gradlew :app:detekt` umbrella (not `:app:detektDevDebug`, not caught by a normal per-module fast-loop check) | The umbrella `detekt`/`verifyAll` graph also pulls in a *non-type-resolution* analysis pass over test sources that has apparently never been exercised/baselined in this repo before (`app/detekt-baseline.xml` and the four flavor baselines had zero entries for the file). Running `detektBaselineTest`/`detektBaselineDevDebugUnitTest` (the *type-resolution* baseline tasks) writes a baseline keyed by a signature string that **includes parameter default values** (`onRowClick: (X) -> Unit = {}`), but the umbrella's actual non-type-resolution pass reports the same function **without** the `= {}` defaults — two different literal keys for the same function, so the freshly-generated baseline never matches and the umbrella keeps failing. | For a trivial pre-existing over-threshold test helper like this, skip the baseline dance entirely — add `@Suppress("LongParameterList")` directly on the function. Confirms clean via `./gradlew :app:detekt` (not `:app:detektDevDebugUnitTest`) since that's the task that actually runs in `verifyAll`. | Don't trust `detektBaselineTest`/`detektBaselineDevDebugUnitTest` (or any `*UnitTest`/`*AndroidTest`-suffixed "with type resolution" baseline task) to satisfy the plain `:app:detekt` umbrella for a **test-source** finding — verify against `:app:detekt` directly, since it's a structurally different analysis pass with a different signature-text baseline key than the type-resolution variants for this exact case. |
| `MatchingDeclarationName` (detekt) on a new `iosMain` file that mixes one top-level class with top-level functions | detekt requires a file whose *single* top-level declaration is a class/object to be named after it. A Kotlin/Native interop file naturally wants both — e.g. `FlowBridge.kt` holding `fun subscribe(...)` plus the `FlowSubscription` handle it returns — and detekt reads that as "single top-level class named wrong", regardless of the functions beside it. Renaming the file to match the class is usually the wrong fix here: the file name determines the generated Objective-C/Swift facade name (`FlowBridgeKt.subscribe`), so renaming silently changes the Swift API. | Split the class into its own file named after it (`FlowSubscription.kt`) and leave the functions in the originally-named file. The facade name Swift calls stays stable and the function-only file has no top-level class to mismatch. | Don't rename the file to satisfy the rule when Swift/ObjC calls its `<FileName>Kt` facade — that's a source-breaking API change on the iOS side for a lint rule. |

## Config-tuning attempts considered and rejected

- **`ignoreAnnotated` on naming/complexity rules for `@Composable`** — not supported by the
  pinned detekt `1.23.8` (see `FunctionNaming` row above). Re-check `gradle/libs.versions.toml`'s
  `detekt` version before retrying this; if the project upgrades detekt, re-verify against the
  new version's `default-detekt-config.yml` (extract from the `detekt-core-<version>.jar`) before
  editing `config/detekt/detekt.yml` — `validation: true` will hard-fail on any unrecognized key.
